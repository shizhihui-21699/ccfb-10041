# 文档泄露检测台

本地运行的文档外发检测控制台。它做两件事：

1. **分段指纹比对**——给受保护文档按段落建立指纹，外发文件即使只截取一两段、改了标点、
   调整了语序或做了改写，也能认出哪份文件的哪几段。
2. **精确数据匹配**——客户名单只以 **HMAC-SHA256 加盐哈希** 保存，外发内容里出现名单上的
   字段组合（姓名 + 手机 / 邮箱 / 客户名 / 账号）就告警。

所有解析、指纹、哈希与比对都在浏览器内完成，没有上传接口。Lit + TypeScript + Vite。

```bash
npm install
npm run samples     # 生成 18 份受保护文档 + 36 份外发样本（含 PDF）
npm run dev         # http://localhost:5173
npm test            # 113 个测试（8 个文件）
npm run eval        # 命令行跑完整样本集，输出准确率/召回率
npm run build
```

首次打开 → 「示例与评测」→「载入并扫描」，即可看到全部样本的判定结果；「运行自动评测」
会按样本自带标注计算指标（与 `npm run eval` 完全一致）。

## 判定是怎么做的

### 切分与归一化

| 步骤 | 做法 | 为什么 |
|---|---|---|
| 切块 | DOCX 段落 / 表格行；XLSX 行；PDF 视觉行合并成段；TXT 行 | 段落是"哪几段"的天然单位 |
| 分词 | 中文按**单字**，西文按词；标点、空白、零宽字符全部丢弃 | 中文分词歧义无解；改标点不应影响指纹 |
| NFKC | 全角/半角、康熙部首（PDF 常见）统一 | 同一份文件从 Word 转 PDF 后字符可能变号 |
| 电话号码 | 只比较数字，`139-0013-9002`、`139 0013 9002`、`+86…` 都归一 | 规避检测最常见的写法 |

### 五个互补信号（每个都可在界面上看到）

| 信号 | 抓什么 | 权重 |
|---|---|---|
| 顺序 k-gram 指纹（8 令牌，64 位） | 整段照抄 | 0.16 |
| IDF 加权重合 | 长文档 / 段落混合 | 0.10 |
| 字符 bigram 重合（标点无关） | 改标点、轻度改写 | 0.26 |
| **最长公共子串**（canonical 字符流） | 重改写中残留的原句 | 0.18 |
| 表格单元袋 + 关键数值 | 列顺序调换、表格↔段落 | 0.20 / 0.08 |

另有无序 k-gram 指纹（同窗口内令牌排序后哈希）覆盖"句内语序调整"。

**防误报的闸门**（这是"主题相近但不该报"能压住的原因）：

- 必须存在**短语级证据**：字符重合 ≥ 0.30，或长公共子串 ≥ 18 字，或表格单元袋吻合；
  仅词汇重合（同一批专业名词）不足以成案。
- `substantial` 下限：精确覆盖 ≥ 30% / 字符重合 ≥ 40% / 单元袋 ≥ 60% / 公共子串 ≥ 20 字，
  或"数值吻合 ≥ 80% **且** 字符重合 ≥ 45%"。共用公司名 + 一个金额不构成告警。
- 短块（< 14 令牌，如标题、单行单元格）要求近乎完全重合，且长度 ≥ 12 字。
- 向下的字符包含关系按长度比衰减，避免"某个常见短语恰好出现在长段落里"被当成截取。

### 客户名单：只存哈希

- 建库时对每个字段值做 `HMAC-SHA256(key, "字段:规范值")`，只保存 32 字节摘要与字段名。
- **密钥不写盘**：默认每次导入生成随机密钥，仅留在内存，刷新页面后需重新导入。
  需要跨刷新复用时可选填口令，走 PBKDF2-SHA256（31 万次迭代）派生，`keyCheck` 用于校验口令。
- 匹配时对外发文本的候选片段做同样哈希再比对，因此**即使拿到浏览器存储也还原不出客户信息**。
- 候选枚举从严：数字字段只取**整段**连续数字（不会把订单号里恰好 11 位当成手机号），
  只有 `86` 开头的国际写法才回退取后 11 位。
- 字段权重：身份证 55 / 账号 46 / 手机 42 / 邮箱 38 / 姓名 26 / 公司 16；
  同一记录 ≥ 2 个字段且相距 ≤ 160 字符时升级为"组合告警"。

### 误报反馈与阈值

告警详情里可「标记误报」（并可对相同证据或整个来源段落启用抑制）或「确认泄露」。
「阈值与反馈」页据此画出 precision/recall 曲线并给出建议阈值；「重算检测结果」按新阈值
即时重算已存检测记录（复用既有令牌流，位置不变）。

## 样本集

`src/samples/corpus.ts` 与 `src/samples/outgoing.ts` 定义，`npm run samples` 落盘为真实文件（PDF 用无头 Chrome 渲染，
带真实文本层与中文 CMap）。

**18 份受保护文档**：docx / xlsx / pdf / txt 各若干，覆盖并购备忘录、股权转让协议、保密协议、
尽调清单、估值模型、客户名单、供应商报价、薪酬带宽、技术方案、产品路线图、渗透测试报告、
法务风险清单、董事会决议、员工手册、投标报价、渠道政策、专利交底书、季度经营分析。

**36 份外发样本**，标注了具体命中的段落与客户记录：

| 类型 | 数量 | 例子 |
|---|---|---|
| 整段照抄 | 17 | 备忘录两段原样贴进周报 |
| 改标点 / 全半角 | 3 | `，`→`,`、`：`→`:` |
| 调整语序 | 5 | 风险句子顺序调换 |
| 改写措辞 | 10 | 换成自己的话发给外部顾问 |
| 截取片段 | 6 | 只取半段放进会议备注 |
| 表格 ↔ 段落转换 | 8 | 效果数据改表格、清单改 Word |
| 中英混排 | 2 | 路线图翻译一半 |
| **对照样本（不该报）** | **5** | 对外公告、行业研究、入职须知、客户拜访总结、询价单 |

对照样本与受保护文档**主题、术语高度重合**（市盈率、扣非净利润、考勤请假、客户公司名），
用来压误报。

### 当前指标（`npm run eval`，默认阈值）

```
段落识别   precision 100.0%   recall 96.1%   F1 98.0%
客户数据   precision 100.0%   recall 100.0%  F1 100.0%
对照样本误报  0 / 5

整段照抄 17/17 · 改标点 3/3 · 调语序 5/5 · 截取 6/6 · 表格转换 8/8 · 中英混排 2/2
改写措辞 8/10
```

漏掉的 2 段都属于"整句重写 + 数字也改成中文数字"，没有任何原句残留——这不是阈值问题，
降低阈值只会增加误报（测试里有这条断言）。这是方法的已知边界：**能认出"留了原句的改写"，
认不出"彻底重写"**。

## 代码结构

```
src/
  core/
    normalize.ts   分词、段落切分、canonical 字符流、大/小写与标点归一
    hash.ts        FNV-1a 令牌哈希、64 位指纹、HMAC/PBKDF2、随机盐
    fingerprint.ts 建库（顺序/无序指纹、IDF、bigram、单元袋、数值）与匹配打分
    pii.ts         加盐哈希建库、候选枚举、字段组合打分
    scan.ts        一次检测的编排、告警生成、抑制、阈值校准
    types.ts       全部类型与默认阈值
  parsers/         docx / xlsx / pdf / text 解析（Node 与浏览器共用）
  ui/              Lit 组件（控制台、告警详情、校准、示例、设置）
  samples/         样本语料定义 + 最小 OOXML 写出器
  demo/            浏览器端样本加载与自动评测（与 CLI 共用实现）
tools/
  generate-samples.ts 生成 public/samples/*（PDF 走无头 Chrome）
  eval.ts             命令行评测 + 阈值扫描
tests/              113 个测试：分词、指纹、PII、解析、端到端、校准、密钥
```

## 已知边界

- **彻底重写识别不了**：既换了全部措辞、又把数字写成中文的段落不会命中（见上）。
- **扫描版 PDF**：没有文本层，会给出明确警告而不是静默通过。
- **图片、加密文档**：不在支持范围。
- **客户名单明文只存在于导入那一刻**：之后若要查看原值需重新导入；这是"只存哈希"的代价。
- 指纹库建在内存中，每次检测重新构建（18 份文档约 5 ms；数千份文档时需改为增量索引）。
